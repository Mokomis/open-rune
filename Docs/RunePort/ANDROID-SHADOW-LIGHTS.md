# Android shadow-light expansion — November 2, 2026

The user requested the higher shadow counts on the installed Android client after the initial Windows-only delivery. **Video → Lighting & shadows → Shadow-casting lights** now exposes **One / Three / Four / Six / Eight nearby**. Requires Remastered lighting. The count is a maximum, not a promise of eight eligible authored sources at every location.

Android shares Windows' eight 1024×1024 depth tiles, 4096×2048 atlas (32 MiB) and unsigned four-bit receiver-light indices. Mac keeps three tiles. The shared renderer already addresses both atlas rows and the eighth lighting lane correctly. Windows' separate conservative CPU shadow-culling optimization remains Windows-only. Existing focused shadow projections and source-selection rules remain unchanged; these are not omnidirectional cubemaps or whole-map shadows.

The Android menu sends its actual count through a dedicated atomic JNI update and a matching startup argument. Choice indices 0/1 retain one/three; indices 2/3/4 mean four/six/eight. Reload uses the separately saved count instead of collapsing it back to the old one-bit value. Legacy world-feature bit 4096 remains boolean, preventing higher counts from overlapping water/AO flags. Original-visual comparison does not overwrite the choice. Diagnostic `shadowLights`, `traceShadows` and `shadowBudgetProbe` activity extras support isolated checks.

## Validation and performance

- All 68 actual shadow GPU readback cases pass: eight atlas slots, mesh/BSP receivers, sign bit, moving/masked silhouettes, neighboring-tile isolation, grouped/ungrouped rendering, invalid slots and frame reset.
- Full Vulkan regression suite passes, including alpha/depth/hit paths, water and lighting buffer offsets, material maps and visual toggles.
- Actual touch menu shows all five choices. Eight can be selected and survives Activity restart; the original three-light preference is restored afterward. The choice dialog fits the tablet screen.
- DM-Hildir PlayerStart4 selects four eligible sources. Requested three renders three; requested eight renders all four. Native GPU scene time is about 9.09→9.36 ms; 240-frame engine samples are 10.00→10.53 ms/frame (about 100→95 FPS), p95 10.61→13.01 ms. These are short sequential fixed-step samples, not displayed/sustained FPS or a thermal-controlled benchmark. There is no locked-120 claim, nor an eight-authored-light performance measurement.
- An initial spawn had only two eligible lights at either maximum (~116/118 engine FPS). It validates startup, not the cost or benefit of more shadows; the placed PlayerStart4 check supplies the meaningful three-versus-four comparison.
- Host-JVM settings checks cover all count mappings, restart persistence, legacy three-light migration, comparison preservation and water/AO isolation. UBSan tests exercise the Android eight-slot layout and the unchanged three-slot layout.
