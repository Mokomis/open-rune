# Original Rune multiplayer: port feasibility and evidence gaps

October 26, 2026. This is a read-only assessment of the user's installed Rune Classic binaries and recovered package scripts against the current Open Rune fork. No networking implementation, APK or tablet state changed. Ghidra-backed REA analyzed focused native functions in the SHA-256-identified `Engine.dll` and `IpDrv.dll`; generated pseudocode is **not** original source. Full raw results remain outside Git under `outputs/original-multiplayer-re/`. See [the binary audit](ORIGINAL-MULTIPLAYER-BINARY-AUDIT.md) for artifact hashes and the first four functions.

## Answer

The original multiplayer design is substantially recoverable. The installed game has a real native packet/channel/replication engine, and recovered scripts specify player movement correction, network roles, Rune combat/game rules and replicated properties. It is technically possible to reimplement those behaviors in Open Rune. There is no self-contained old multiplayer module that can be linked into its native ARM64 process: its routines depend throughout on Unreal object metadata, bytecode evaluation, serialization, actor lifecycle, package loading and game-loop roles that are absent or incomplete in the fork.

The current evidence is enough to plan a compatible engine implementation; it is **not yet enough to claim byte-for-byte compatibility with an original server**. That requires full serialization coverage and packet fixtures from a controlled original-game exchange. The user considered original-server compatibility, then chose an Open Rune server using our newer authenticated transport so custom combat moves can work. The old wire is therefore research for a possible later classic-rules mode, not the current implementation target.

## Current fork boundary

Open Rune's `UNetDriver`, `UNetConnection`, `UChannel` and `UActorChannel` classes are shells. The VM loads network flags and replication offsets but does not route script calls. Normal gameplay uses a local viewport and pauses the level when its menu opens. The opt-in `RuneNetwork` adapter already admits input/actions, captures a limited world state and presents replicas, but its fixture runs two sessions in one process; there is no independently joined original-protocol client or server. `OPENRUNE_ENABLE_NETWORK` defaults off. See [the engine checkpoint](NETWORK-ENGINE-CHECKPOINT.md).

## Evidence still required for an old-protocol client

1. **Exact version and endpoint:** Confirm which DLL revision the installed `Rune.exe` loads; the directory also contains `101` and `107` variants. Capture an original server/client negotiation with owned game data. The INI selects `IpDrv.TcpNetDriver`, but configuration is not a live connection trace.
2. **Golden wire fixtures:** Record matching plaintext control messages and packet bytes for hello/login, idle, movement, actor spawn, attack, damage, disconnect and map change. Tie each to the specific binary hashes and package GUIDs. A decompiler alone does not prove parser interoperability.
3. **Serialization closure:** Reconstruct bit writer/reader behavior, name/object/package mapping, every networked property type needed for Rune, function argument encoding, actor initial state, defaults, field index ordering and package generations. Validate against independently captured bytes, not just matching decompiler pseudocode.
4. **Lifecycle closure:** Exercise connection state, timeout, loss/reordering, channel ACK/NAK, file/package mismatch, late join, level transition, respawn, reconnect and client suspend/resume. Use two processes and an original game endpoint if compatibility is desired.
5. **Security and scope:** If classic compatibility is later requested, treat the old handshake/packet format as a separate compatibility protocol with a separately reviewed trust boundary. This is an engineering inference, not a completed security audit of the original game.

## Practical decision

The current target is an Open Rune server, our authenticated protocol and explicit Rune actor adapter. We will reuse original **game rules and movement behavior** where appropriate while giving kick, shield bash and other new mechanics authoritative server outcomes. Unmodified original servers cannot apply those outcomes or enforce their cooldowns, shield response and displacement. Implementing the old wire remains a possible later classic-rules mode only after the evidence gates above. This is a judgment from the observed dependency depth; no two-process implementation comparison has been run.
